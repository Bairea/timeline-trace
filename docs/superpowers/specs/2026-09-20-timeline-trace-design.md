# timeline-trace 设计文档

> 理想时间线 vs 实际时间线 的对照与沉淀工具
> 日期：2026-09-20
> 状态：待用户审阅

---

## 1. 定位与范围

单人自用的「理想时间线 vs 实际时间线」对照与沉淀工具。它不管理任务、不管 deadline、不做提醒推送，只做一件事：把每天真实的时间分配如实记下来，与理想工作日模板自动比对，让偏差和计划外时长可见。

### 在范围内

- 理想模板的定义与编辑（可复用工作日模板）
- 实际时间块的记录（白天随手敲一行 / 拖块 / 框选）
- 自动比对与状态判定
- 块的可视化编辑（拖动、改时长、改名、删除、撤销）
- 精确导出（CSV / XLSX）
- 统计视图（日 / 周 / 月，优先级四项达标率）

### 明确不做（YAGNI）

- 多用户、账号体系、分享
- 移动 App（浏览器访问即可，手机以只读查看为主）
- 自动追踪（不做屏幕监控、不读手机使用记录）
- 任务 / 待办管理
- 提醒、推送、打卡通知

## 2. 理想模板（用户的基准线）

### 2.1 四条优先级（判定的价值排序，不是标签）

1. **睡眠** — 绝对第一。目标不是「23:00 上床」而是「23:00 已睡着」，故 22:20 起进入收尾、22:40 上床。最低保证 7 小时，任何项目、游戏、小说都不能借用睡眠时间。
2. **早晚健身操** — 每天的身体锚点，早上 5–10 分钟、晚上 10–20 分钟。重点是每天做，不追求练狠。跳绳、深蹲、拉力带属加餐，不算硬指标。
3. **情绪稳定** — 每天必须有「没有绩效目的」的低刺激时间（正经书 / 练字 / 散步 / 适量游戏任选）。此时间不是浪费，而是防止晚间通过小说、视频报复性补偿。
4. **项目推进** — 稳定推进，但必须排在前三项之后。工作日每天 45–90 分钟高质量推进即足够。

### 2.2 手机与娱乐管理

目标不是禁掉娱乐，而是减少「无意识娱乐」。游戏可主动玩、小说可主动看；短视频、信息流、躺床刷手机优先削减。

## 3. 数据模型

SQLite 单文件。四张表为基础数据，其余一切（对照、统计、导出）均为计算所得。

```sql
-- 理想模板（结构上支持多模板，当前仅「工作日」一条）
CREATE TABLE templates (
  id          INTEGER PRIMARY KEY,
  name        TEXT NOT NULL,
  description TEXT,
  is_default  INTEGER NOT NULL DEFAULT 0,
  created_at  TEXT NOT NULL
);

-- 模板内的时间块
CREATE TABLE template_blocks (
  id          INTEGER PRIMARY KEY,
  template_id INTEGER NOT NULL REFERENCES templates(id) ON DELETE CASCADE,
  start_min   INTEGER NOT NULL,   -- 自 00:00 起的分钟数
  end_min     INTEGER NOT NULL,   -- 跨零点时 > 1440
  name        TEXT NOT NULL,
  category    TEXT,               -- 睡眠/身体锚点/情绪稳定/项目推进/通勤/事务/其他
  sort_order  INTEGER NOT NULL DEFAULT 0
);

-- 某天使用哪个模板
CREATE TABLE day_instances (
  date        TEXT PRIMARY KEY,   -- YYYY-MM-DD
  template_id INTEGER REFERENCES templates(id),
  note        TEXT
);

-- 实际记录的时间块（核心表）
CREATE TABLE actual_blocks (
  id          INTEGER PRIMARY KEY,
  date        TEXT NOT NULL,      -- 归属日，跨零点块归属起始日
  start_min   INTEGER NOT NULL,
  end_min     INTEGER,            -- NULL = 进行中（开放区间）
  name        TEXT NOT NULL,
  is_low_stimulus INTEGER NOT NULL DEFAULT 0,  -- 标记为「无绩效目的的低刺激时间」
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL,
  deleted_at  TEXT                -- 软删除标记，NULL = 有效
);
CREATE INDEX idx_actual_date ON actual_blocks(date) WHERE deleted_at IS NULL;
```

### 3.1 关键设计决定

1. **时间一律存分钟数整数**（`06:30` → `390`），不存字符串。计算重叠、时差、导出都在整数域进行，无解析歧义。跨零点睡觉以 `1380` → `1830` 表示，导出时还原为 `22:40 / 06:30`。

2. **`category` 是自由字段 + 固定候选值**，不做数据库级枚举约束。四条优先级是判定价值排序而非标签——「无绩效目的的低刺激时间」可能表现为读书、练字或散步，无法靠 category 穷举，需另行处理（见 §5.4）。

3. **`day_instances` 独立成表**，为将来可能新增的周末模板预留。当前默认全部指向「工作日」；某天若无记录即为空，不算任何缺失。

4. **比对结果不落库。** `status`、`delta_start_min` 等均为查询时实时计算。原因是模板会持续调整（例如「干活」从 20:30 挪到 20:15），若比对结果落库，改一次模板就要刷新全部历史。实时计算的代价仅为毫秒级。

5. **块允许重叠。** 真实生活存在重叠（听书通勤时同时思考）。不做强约束禁止，仅在统计时提示。硬约束会阻碍记录习惯的坚持。

6. **跨零点块归属起始日。** 睡眠块 22:40 → 次日 06:30 记在起始日，保证「睡了多久」可一次性计算，无需次日手工拼接。

## 4. 系统结构

单 Python 进程，模块职责互不越界。

```
timeline-trace/
├── app/
│   ├── main.py          FastAPI 应用、路由注册、静态文件挂载、认证中间件
│   ├── db.py            SQLite 连接、建表、迁移、备份辅助
│   ├── models.py        Pydantic 模型（请求/响应 schema）
│   ├── compare.py       ★ 对照引擎：纯函数，无 IO
│   ├── stats.py         统计聚合：纯函数，只消费 compare 输出
│   ├── export.py        CSV / XLSX 生成
│   └── api/
│       ├── templates.py 模板 CRUD
│       ├── actual.py    实际块 CRUD + 快速记录解析
│       └── reports.py   对比结果、统计、导出
├── static/
│   ├── index.html       单页
│   ├── app.js           原生 JS
│   └── style.css
├── tests/
│   ├── test_compare.py  对照引擎穷举测试（重点）
│   ├── test_parser.py   快速记录文法测试（重点）
│   └── test_export.py
├── data/timeline.db     SQLite
└── requirements.txt
```

### 4.1 两条最重要的边界

**① `compare.py` 是纯函数，不碰数据库。**

```python
def compare_day(template_blocks: list[TemplateBlock],
                actual_blocks: list[ActualBlock]) -> list[BlockComparison]
```

输入两组块，输出带状态的对照结果。不读库、不写库、不读当前时间。因此**可被单元测试穷举**：重叠边界、跨零点、完全错开、一个模板块由多个实际块拼凑等情形，全部是纯数据进出。这是系统内唯一含真实逻辑之处，值得隔离。

**② `stats.py` 只消费对照结果，不重新计算重叠。**

将 `compare_day` 的输出按日期聚合，避免「统计口径」与「页面显示」两套算法不一致——这类不一致最难排查。

## 5. 对照引擎

### 5.1 判定规则（按模板块逐条计算）

| 情况 | status | 说明 |
|---|---|---|
| 重叠 ≥ 60% 模板时长 | `aligned` | 记录 `delta_start_min`、`delta_dur_min` |
| 重叠 1% – 60% | `offset` | 有交集，但错位或时长不足 |
| 模板块当天无任何实际块重叠 | `unrecorded` | 灰色，**不计入未达标** |
| 实际块与所有模板块重叠均为 0 | `unplanned` | 计划外，计入当日计划外总时长 |
| 实际块 100% 被模板块包含且时长足够 | `aligned` | 常规命中 |

判定是**按模板块逐条计算**的，不是给实际块打一个全局标签。因此一个实际块可同时对模板块 A 记 `aligned`、对模板块 B 记 `offset`。导出表中 `template_block` 为空的行即 `unplanned`。

**`status` 取值域固定为四档：`aligned` / `offset` / `unrecorded` / `unplanned`。** 时长不足但仍与模板块有交集的情形归入 `offset`（导出表中以负的 `delta_dur_min` 体现），不另设 `short` 等取值，避免状态枚举膨胀。

### 5.2 容差对齐

生活时间表不可能分钟级吻合。若要求精确匹配，用户会天天被判「不达标」，记录习惯必然中断。故：

- 起点偏差 ≤ 15 分钟且时长偏差 ≤ 15 分钟，仍记为 `aligned`，但记录实际偏差值
- 超出容差则按 §5.1 降级为 `offset`

容差值（默认 15 分钟）放在配置项中，便于后续调整。

### 5.3 状态四档的语义区分

- `unrecorded`（未记录）与 `offset`（未达标）**必须分开**。否则会把「忘记记」与「没做到」混为一谈，数据即失真。
- `unplanned`（计划外）是核心信号：它标记了模板中不存在的时间去向，正是「无意识娱乐」的可观测入口。

**状态与导出字段的对应关系（唯一口径）：**

| status | `template_block` | `delta_*` | 说明 |
|---|---|---|---|
| `aligned` | 命中的模板块名 | 有值 | 实际块命中某模板块，含容差内的偏差 |
| `offset` | 命中的模板块名 | 有值（时长可为负） | 有交集但错位或时长不足 |
| `unplanned` | 空 | 空 | 模板中无对应的实际块 |
| `unrecorded` | 模板块名 | 空 | 该模板块当天无实际块，此行仅含模板侧时间 |

一个模板块当天若命中多个实际块，则该模板块生成多行对照结果，`status` 取其中最优的一档；导出明细以实际块为主键逐行展开。

### 5.4 优先级四项的度量口径

四项优先级不是标签，而是需要单独定义的度量：

| 优先级 | 度量方式 |
|---|---|
| 睡眠 | 当日睡眠块总时长，与 7 小时下限比对；记录入睡起始时刻，与 22:40 目标比对 |
| 早晚健身操 | 当日是否存在 `category=身体锚点` 的块，且时长落在 5–20 分钟区间内 |
| 情绪稳定 | 当日是否存在被显式标记为「无绩效目的」的实际块（该标记为实际块上的独立布尔字段，独立于 category） |
| 项目推进 | 当日 `category=项目推进` 的实际块总时长，与 45–90 分钟区间比对 |

因「情绪稳定」无法由名称自动推断，实际块上设一个可选的 `is_low_stimulus` 布尔字段，由用户在记录时或事后标记。未标记则该日此项计为「未记录」。

## 6. 记录交互

### 6.1 三种输入入口（同一结果）

**入口 1 · 快速记录框（主用，键盘流）**

```
20:30-21:10 干活        → 完整区间
20:30 干活              → 只有起点，接上一块终点，默认 30 分钟
20:30- 干活             → 开放区间（进行中），当日可补终点
```

块名从模板候选自动补全；输入模板中不存在的名称（如「短视频」）自动标记为 `unplanned`。

**入口 2 · 拖动（微调）**

已生成的块可上下拖动、拖边缘改时长。拖出模板范围自动转 `unplanned`。键盘微调：选中块后 `↑↓` 挪 5 分钟，`Shift+↑↓` 挪 15 分钟。

**入口 3 · 时间轴空白处框选**

在 24h 轴空白区间拖出矩形，立即弹出迷你输入框填写名称。适合「不想打字、先框住再说」。

### 6.2 块的可视化操作

| 操作 | 触发方式 |
|---|---|
| 删除 | 块上悬停出现 `×` 点击即删；或选中块按 `Delete` |
| 改时间 | 上下拖整块；拖上/下边缘改时长 |
| 微调 | 选中后 `↑↓` 挪 5 分钟，`Shift+↑↓` 挪 15 分钟 |
| 改名字 | 双击块名就地编辑 |
| 补终点 | 点击未闭合块的脉冲提示，填入结束时间 |

### 6.3 删除的三个决定

1. **真删除 + 立即撤销，不弹确认框。** 删除后右下角出现 `已删除「短视频」 [撤销]`，停留 5 秒。一天要删多次的场景下，模态确认框是纯负担；容错靠可逆而非确认。
2. **点击撤销后为硬删除，但仍写 `deleted_at` 软删除标记。** 这是长期积累的数据集，事后回忆「上周三那个块删错了」时，无软删除即永久丢失。代价仅为查询多一个 `WHERE deleted_at IS NULL`。
3. **模板块不能直接删，只能改。** 模板是比对基准线，若可随手删除则基准会漂移。删除模板块须进入模板编辑页，刻意多一道手续。

### 6.4 批量操作

轴上按住 `Shift` 拖出选框可选中多个块，统一删除或统一移动。白天补记录时常需一次补三五块，逐块操作过慢。

## 7. 快速记录解析器与错误处理

### 7.1 解析文法（`actual.py` 内纯函数）

```
规则（按优先级）:
1. 完整区间  HH:MM-HH:MM 名称
2. 只有起点  HH:MM 名称     → 起点接上一块终点；无上一块则从当前时刻起算 30 分钟
3. 开放区间  HH:MM- 名称    → 起点 → null（进行中），当日可补终点
4. 只有区间无名称           → 用模板候选补全；跨模板区间则命名「未命名」

容错:
· 20.30 / 20：30 / 2030 / 8:5 均接受
· 全角冒号、全角横线统一归一化
· 名称两端空白裁剪，中间空格保留
```

### 7.2 三条刻意的设计选择

1. **解析失败绝不静默丢弃。** 输入无法解析时 API 返回 422 并携带原始文本，界面在该行下方标红提示。记录动作发生在碎片时间，若敲错后无声丢失，到周末才会发现历史有洞，数据即失效。

2. **「接上一块」为默认行为但可关。** 连续记录（`12:00 午饭` 后接 `12:45 工作`）时最省事；但若两块间存在真实空档（20:15 坐下却想记 20:30 的事），该默认会静默吞掉 15 分钟。故界面提供「从上一块接着算」开关，默认开启。

3. **开放区间是一等公民。** 白天随手记时，20:30 坐下开始干活即可能想记一笔，但当时不知会持续到几点。该设计允许先记着、之后补终点，避免事后回忆「我好像 20:30 开始的」。未闭合块在页面上带脉冲高亮提醒补完。

### 7.3 错误处理总原则

| 场景 | 处理 |
|---|---|
| 时间格式无法解析 | 422 + 原文本回显，界面标红，不写库 |
| 结束早于开始 | 视为跨零点；若跨度 > 16h 则报错（可能敲错） |
| 时间超出 00:00–24:00 | 拒绝，提示可能漏了前导位 |
| 与已有块重叠 | **允许**，仅在该块显示重叠角标，不阻断 |
| 数据库写失败 | 返回 500，界面**保留输入框内容不清空**，可直接重试 |

最后一条是记录类工具的生命线——丢失一次输入，用户即不再信任该工具。

## 8. 导出与统计

### 8.1 导出格式（明细）

每行 = 一个时间块：

```
date,start,end,duration_min,block_name,template_block,status,delta_start_min,delta_dur_min,is_planned
2026-09-20,06:35,07:02,27,早操,早操,aligned,5,-3,false
2026-09-20,12:20,13:05,45,午饭与午休,午饭与午休,offset,20,0,false
2026-09-20,20:30,21:10,40,干活,干活,offset,0,-50,false
2026-09-20,21:10,21:30,20,短视频,,unplanned,,,true
2026-09-20,22:20,22:40,20,晚练,晚练,unrecorded,,,false
```

- `duration_min` 精确到分钟，求和即当日已记录总时长
- `delta_start_min` / `delta_dur_min` 为相对模板的偏差分钟数，可直接在 Excel 内分析
- `template_block` 为空 = 计划外

### 8.2 导出形式

- **CSV**：UTF-8 BOM，Excel 可直接打开
- **XLSX**：多 sheet —— 明细 / 日汇总 / 区间统计
- 支持按日期范围导出与全量导出
- 原始数据留存本地，网页只做读写与可视化

### 8.3 统计视图（同一份 block 数据算出的视图，不另存表）

- **每日**：各类目时长、计划外总时长、睡眠起止
- **区间**：周 / 月聚合趋势
- **优先级四项**：睡眠达标率、早操出勤率、无绩效时段存在率、项目推进时长

```bash
python -m uvicorn app.main:app --reload --port 8000
```

本地 `127.0.0.1:8000`，SQLite 位于 `data/timeline.db`。依赖收在 `requirements.txt`（fastapi、uvicorn、pydantic、openpyxl），venv 建于项目内。

### 9.2 云服务器部署

```bash
# uvicorn 只监听回环
uvicorn app.main:app --host 127.0.0.1 --port 8000
# nginx 反代 443 → 127.0.0.1:8000
# systemd 托管 uvicorn，开机自启、崩溃重拉
```

### 9.3 TLS 方案：自签证书（用户已选定方案 A）

服务器有公网 IP、无域名。签发给 IP 的证书无公共 CA 免费提供，故采用自签证书：

- nginx 使用自签证书对外提供 HTTPS
- 浏览器首次访问需手动信任（点击「继续访问」）
- 每台新设备需操作一次

**已知风险（明确记录）：** 自签证书无法防御中间人攻击——证书不被公共信任链背书。加密仅覆盖链路传输，不提供身份保证。若后续对安全性要求提升，建议后续投入约 ¥30–70/年购入域名并申请 Let's Encrypt 免费证书，可一次性消除该风险。

### 9.4 无论何种方案都必须做的三件事

1. **访问口令**：环境变量 `APP_PASSWORD`，登录后签发 HttpOnly Cookie。单人自用无需账号体系，一个口令足够，但**必须有**——公网 IP 会在数小时内被全网扫描器发现。
2. **每日自动备份**：`sqlite3 .backup` 或直接拷贝 db 文件至带日期的备份目录，保留 30 天。SQLite 单文件的优势正在于此，备份脚本仅需三行。
3. **不暴露 8000 端口**：安全组仅开 443 与 22，uvicorn 只监听回环。这是最易犯的低级错误。

### 9.5 手机端体验

以只读为主：可查看当天对照与统计。记录操作仍以电脑为主——工作日用户本就在电脑前。

## 10. 测试策略

系统的真实逻辑集中在两处，测试亦集中于此：

| 模块 | 测试内容 |
|---|---|
| `test_compare.py` | 重叠边界（0% / 1% / 59% / 60% / 100%）、跨零点块、完全错开、一个模板块由多个实际块拼凑、容差边界（14 / 15 / 16 分钟）、多重匹配 |
| `test_parser.py` | 三种文法形态、全角字符归一化、各种时间写法（`20.30` / `2030` / `8:5`）、解析失败返回原文、接上一块逻辑、开放区间 |
| `test_export.py` | CSV 转义（字段含逗号）、UTF-8 BOM、XLSX sheet 结构、跨零点时间还原、空数据导出 |

`compare.py` 与 `parser.py` 均为纯函数，测试无需数据库与网络，可快速穷举边界。
