## 1. P0 — `category` 无取值校验，构成存储型 XSS

### 事实

`app/api/templates.py` 对 `category` 只做字段白名单，不做取值校验：

```python
# 第 86 行，POST
(template_id, start, end, name, payload.get("category"), nxt)
#            ^^^^ 校验了      ^^^^ 未校验，任意字符串直接入库

# 第 97 行，PUT
allowed = {"start_min", "end_min", "name", "category", "sort_order"}
#                                        ^^^^^^^^ 在白名单里，但同样无取值校验
```

而 `static/template.js:129` 把它**未转义**地拼进 HTML 属性：

```js
`<option value="${c}"${c === b.category ? ' selected' : ''}>${c}</option>`
```

注意同一行的 `b.name` 是转义过的（`render()` 第 138 行 `escapeHtml(b.name)`）——
**作者对名字有转义意识，但漏了 category**。

### 复现

```bash
.venv/Scripts/python.exe -c "
from fastapi.testclient import TestClient
import tempfile, pathlib
import app.db as db
d = pathlib.Path(tempfile.mkdtemp()); db.DB_PATH = d/'t.db'
from app.main import app
with TestClient(app) as c:
    payload = {'start_min': 100, 'end_min': 200, 'name': 'x',
               'category': '\" onmouseover=\"alert(1)'}
    print(c.post('/api/templates/1/blocks', json=payload).status_code)
"
```

实测输出：

```
POST 恶意 category -> 200 {'id': 19}
库里存的是什么: '" onmouseover="alert(1)'
```

写入成功。该值随后会进入模板编辑页，逃出 `value` 属性成为事件处理器。

### 影响面评估（不夸大）

- **触发前提**：攻击者需已通过认证（`/api/templates` 挂在 `require_session` 之下）。
- **因此这不是「外部可打」的漏洞，而是「认证后用户可自伤 / 多用户场景下互伤」**。
  本项目是单用户工具，实际风险有限。
- **但修复成本极低，且根本问题是「取值范围该由代码约束」**。category 是
  统计口径的锚点（`config.py:CANDIDATE_CATEGORIES` 已定义 7 个候选值），
  让任意字符串写进去本身就会破坏统计语义——XSS 只是它的极端表现。

### 修复方向

在 `_validate` 同层加一个 `_validate_category()`，对 POST 与 PUT 统一生效
（与 start/end/name 同样的理由：只校验创建不校验修改等于漏一半）。
允许 `None`（未分类）。

## 2. P1 — ~~规则②绕过时间校验~~ **（评审后判定为不需要修复，已撤回）**

> **本节结论在修复阶段被推翻。** 保留原文与推翻过程，因为这是一个
> 「听起来对、实际会削掉产品核心价值」的典型误判，值得后来者看到。

### 我最初的事实认定（成立）

`app/classify.py` 的匹配规则②（去括注后名字互相包含）不检查时间重叠：

```python
if a_base:
    for t in candidates:
        t_base = _base_name(t.get("name"))
        if t_base and (t_base == a_base or t_base in a_base or a_base in t_base):
            return t["category"]        # ← 从未看过 start_min/end_min
```

复现（实际块在凌晨 16:40–16:50，与任何模板块都无交集，却拿到 category）：

```
顺序 A (长名在前): 项目推进
顺序 B (短名在前): 项目推进

注意：实际块在 1000-1010，与 0-60 和 510-720 都无重叠，
却仍被赋予 category —— 规则②完全绕过时间校验
```

### 我据此提出的修复（错误）

给规则②加时间重叠前置条件，理由是「名字是强信号，但不该强到无视时空一致性」。

### 为什么这个修复是错的

修复后跑真实数据，**发现回归**：`data/timeline.db` 里的真实记录
`785–845 干活`（60 分钟）的项目推进统计从 60 变成了 0。

原因：模板里上午 08:30–12:00 叫「工作」，而「干活（中间做拉伸）」排在 20:30–22:00。
用户把「干活」记在了上午 → 名字匹配上了，但时间不重叠 → 被新约束挡掉。

**反思后我认识到：名字不是「匹配模板块」的线索，而是用户对「这是什么事」的直接声明。**
用户打了「干活」，就是在说他处于干活状态——时间放在上午还是晚上，不影响这件事的分类。

更关键的是：**时间错位恰恰是这个工具最该暴露的东西**。`compare.py` 的整个
存在意义就是发现「计划 20:30 干活，实际 12:45 干了」这类偏差。统计层若要求
名字匹配必须与模板块时间重叠，等于把对照引擎发现的东西又悄悄丢掉。

我最初构造的测试用例（「凌晨的读书」vs「早上的读书笔记整理」）在直觉上像问题，
但推到底：如果用户真的凌晨 2 点读了书，而模板里读书排在 20:15，**他就是读了书**，
应当计入「情绪稳定」——这正是一条值得被记录的时间错位。

### 最终处置

**撤回该修复**，并在 `classify.py` 与 `tests/test_stats.py` 写明「名字匹配刻意不看时间」
这条决定及其理由，防止后人再次「顺手修正」。

- `test_name_match_ignores_time_on_purpose`：用真实数据（785–845 干活）固定住该行为
- `test_empty_name_falls_back_to_time`：确认时间兜底仍只在无名字线索时启用

规则③（时间兜底）保留不变——它本来就靠时间推断，无名字可用。

### 教训

**「加一道校验」总是听起来更安全，但在语义层可能是过度约束。**
我如果没有跑真实库，这条回归就不会被发现——测试全绿而真实数据丢失，
是最危险的一类缺陷。这也印证了记忆里那条：**结论必须有可执行验证支撑**。

## 3. P1 — `CATEGORIES` 前后端不一致（7 vs 6）

### 事实

```
config.py : 7 ('睡眠', '身体锚点', '情绪稳定', '项目推进', '通勤', '事务', '其他')
template.js: 6 ['睡眠', '身体锚点', '情绪稳定', '项目推进', '通勤', '事务']

差集 (config 有 / js 无): {'其他'}
```

### 为什么这在本次改动后变得更严重

`app/classify.py` 新增了 `UNCATEGORIZED = "其他"`，并且会**主动产出**这个值
（无法归类时）。于是产生两个后果：

1. **显示错误**：模板里 category 为「其他」的块，下拉框会落到 `<option value="">未分类</option>`，
   看起来像没分类。用户一旦碰了这个下拉框，保存时就把 `"其他"` 写成 `null`——
   **静默丢掉一个有效取值**。
2. **提示误导**：`renderCatChips()` 会把「其他」列进「未使用」列表，
   但这个值恰恰是会被系统自动产生的。

### 修复方向

前端 `CATEGORIES` 应含「其他」。更好的做法是**不再维护第二份常量**——
把候选值从后端读（`GET /api/categories` 或随 `/api/templates` 一起返回），
避免第三处再次分叉。

## 4. P1 — 无名字线索时，短记录系统性落榜

### 事实

规则③要求重叠**占模板块**的比例 ≥ `MIN_OVERLAP_RATIO`（0.5）。对长模板块，
这个门槛极高：

```
  早操             模板块   30min  需至少记录   15.0min  占模板 身体锚点
  通勤、听书、走路       模板块   55min  需至少记录   27.5min  占模板 通勤
  工作             模板块  210min  需至少记录  105.0min  占模板 项目推进
  工作             模板块  255min  需至少记录  127.5min  占模板 项目推进
  干活（中间做拉伸）      模板块   90min  需至少记录   45.0min  占模板 项目推进
  睡觉             模板块  470min  需至少记录  235.0min  占模板 睡眠
```

后果演示（实际块名叫「专注写代码」，与模板名无包含关系）：

```
  专注写代码  30min (模板工作 210min) -> 其他
  专注写代码  60min (模板工作 210min) -> 其他
  专注写代码 105min (模板工作 210min) -> 项目推进
  专注写代码 120min (模板工作 210min) -> 项目推进
```

**「我今天工作了半小时」是完全正常的记录方式，但记 30 或 60 分钟都统计不到。**

### 根因：阈值借错了

我在实现时从 `compare.py` 借了 `MIN_OVERLAP_RATIO = 0.5`，理由是「与对照引擎
同一把尺子，避免口径分裂」。**这个论证是错的**——两个场景判的是不同的事：

| 场景 | 判什么 | 分母该是什么 |
|---|---|---|
| `compare.py` | 这个**模板块**算不算被覆盖了 | 模板块时长 |
| `classify.py` | 这个**实际块**属于哪一类 | 实际块时长 |

对照引擎问「这一格有没有被履行」，分母自然是模板块；分类问「这件事属于哪一类」，
分母该是实际块。**借同一个常数掩盖了两者语义不同。**

### 修复方向

规则③的分母改为**实际块时长**（即 `ov / a_span >= ratio`），并把比率
可配置化（挪进 `config/thresholds.yaml`）。但需注意：这正是我上一轮
**刻意改掉**的版本——当时发现「占实际块比例」会让「干活时段里的短视频」
被误判为项目推进。

所以正确解法不是简单换分母，而是**分层**：

- 规则①（名字精确相等）：无条件采用
- 规则②（名字包含）：加时间重叠前置（见 §2）
- 规则③（时间兜底）：分为两种情形
  - 实际块**完整落在**某模板块内 → 占实际块比例（短记录能归位）
  - 实际块**跨越**模板块边界 → 占模板块比例（防摸鱼被吸收）

「短视频」的时长（30min）与「干活」模板块（90min）是包含关系且占比 33%，
按新规则它会因「完整落在内 + 占自己 100%」而被归为项目推进 ——
**需要额外一条判据**才能挡住它。候选方案：当模板块内存在多个实际块时，
只有**时长最长**的那个（或名字与模板一致的）继承 category。

**这一条我没有确定的答案，需要你拍板。** 见 §7 待决策。

## 5. P2 级问题

### 5.1 `source` 只写不读，且语义无法实现其声称的用途 —— **已删除**

我上一轮批评 `category` 「只写不读」，然后**自己加了同样性质的字段**：

```
$ grep -n "source" app/ -r
app/seed.py:40:  "INSERT INTO templates (..., source) VALUES (..., 'seed')"
app/db.py:17:    source TEXT NOT NULL DEFAULT 'user'
app/db.py:68:    ("templates", "source", "ALTER TABLE ... DEFAULT 'user'")
```

三处全是写或定义，**没有任何一处读**。

更严重的是**语义本身是错的**：迁移语句用 `DEFAULT 'user'`，意味着
任何从旧版本升级上来的库，那条模板都会被标成 `user`——而它其实是
旧版本代码灌进去的。于是：

- 区分不出「用户真的改过」和「旧版本灌的」；
- `seed.py:15` 的注释说这是「为将来可能需要的『重新种子化』留判断依据」，
  但按当前语义，**这个用途实现不了**。

**处置：删除。** 同时补上真正需要的「重新种子化」入口
`reseed_from_config()`（显式调用，而非每次启动偷偷覆盖）。

`db.py` 的迁移机制相应拆成 `_ADD_COLUMNS` / `_DROP_COLUMNS` 两组，
后者用 SQLite 3.35+ 的 `ALTER TABLE DROP COLUMN` 清理旧库。
测试覆盖：带 `source` 列的旧库启动后被清掉且数据无损、迁移重复跑不抛错。

**教训：加字段前先想清楚「谁读它、读到之后做什么」。想不出来的话，
那个字段本身就是答案。**
留一个语义错误又没人读的字段，比不加更糟——它会让后来者以为有过某套逻辑。

### 5.2 `sort_order` 在 PUT 里可被任意修改 —— **已修**

`allowed` 含 `sort_order`，但显示顺序的语义是「文件顺序 / 时间顺序」。
改成任意值会让列表顺序与时间不一致，且无任何地方会纠正它。
**处置：从 `allowed` 移除**，并加测试 `test_update_cannot_change_sort_order`
确认改它不影响列表顺序。

### 5.3 `test_add_block_actually_persists` 未断言 category 落库 —— **已补**

该测试传了 `category: "项目推进"`，但只断言了名称与时间：

```python
assert (added[0]["start_min"], added[0]["end_min"]) == (100, 130)
```

`test_update_block_category_persists` 只测了合法值「睡眠」。

**这正是 P0 逃过测试的原因**：没有任何一条测试问过「传非法 category 会怎样」。
`test_update_ignores_unknown_fields` 的 docstring 写着「绝不能写进库」，
说明作者对字段白名单有意识，但没把同样的意识用到取值范围上。

**处置：** 新增 8 条 category 相关断言（拒绝非法值、错误消息含候选值、
接受全部候选值、接受 null、清除分类、category 确实落库）。

### 5.4 `classify.py` 规则②的子串方向 —— **保留，观察**

```python
if t_base and (t_base == a_base or t_base in a_base or a_base in t_base):
```

`a_base in t_base` 方向意味着一个很短的通用名字会被任意长的名字吸附。

**处置：暂时保留。** 原本担心它配合「无时间校验」会放大风险，但 §2 已
证明时间校验不该加（会削掉时间错位的价值），所以这条不构成额外风险——
短名字被长名字吸附在语义上恰恰是对的：用户打「读书」，模板里有
「读书笔记整理」，他大概率就是在做那件事。

**真正的防护是规则顺序**：精确相等优先于包含关系，所以「读书」若能
精确匹配某个模板块，就不会被「读书笔记整理」吸走。这条性质已有测试覆盖。

## 6. 经实测**不成立**的怀疑（撤回）

诚实记录，避免后人重复排查。

### 6.1 ~~遍历顺序导致结果不稳定~~

**我的怀疑**：规则②用 `for t in candidates` 顺序遍历，若两个候选都能命中，
结果取决于顺序。

**实测**：

```python
result = infer_category(r, tpl_a) != infer_category(r, reversed(tpl_a))
# -> False，两种顺序结果一致
```

**不成立**。因为 `t_base == a_base`（精确相等）判在包含关系之前，
实际场景中精确匹配先命中，顺序无影响。我构造不出能触发的反例。

（§2 的那个案例里结果也稳定，真正的问题是绕过了时间校验。）

### 6.2 ~~`/api/stats` 的 N+1 查询~~

**我的怀疑**：`reports.py:91` 在日期循环内对每天调 `_compare_for`，
而它每次都重查模板与模板块；本轮新增的 `infer_category_map` 会放大这个开销。
查 366 天就是 366 次模板查询。

**实测**：

```
  1 天: 0.036s  (35.8ms/天)
 30 天: 0.381s  (12.7ms/天)
 90 天: 1.087s  (12.1ms/天)
 90 天(单日20条): 1.101s
```

**不成立**。90 天 1.09 秒，单日成本恒定在 ~12ms 且不随记录数增长。
SQLite 本地查询 + 模板仅 18 行，N+1 的实际代价可忽略。
按「先实测、无收益就不优化」的原则，**不做缓存重构**。

（若将来模板数量或单日记录量大幅增长，可再测。）

## 7. 待决策：规则③的分层方案

§4 的修复需要你的判断，因为它涉及**指标语义的取舍**：

核心矛盾：同样是「完整落在模板块内的短记录」，

- 「专注写代码 30min」落在「工作 210min」内 → **希望归为项目推进**
- 「短视频 30min」落在「干活 90min」内 → **希望归为其他**

二者在「名字 vs 时间」维度上的信号强度相似（都是名字不匹配、时间被包含）。
要区分它们，只能引入额外判据。候选：

| 方案 | 做法 | 代价 |
|---|---|---|
| A. 名字优先（当前） | 名字不匹配就不归类 | 「专注写代码」丢统计 |
| B. 时长最长者继承 | 模板块内只让最长的那块继承 category | 「短视频」在只有它时会误判 |
| C. 占实际块比例 | 完整落在内即归位 | 「短视频」被吸收（上一轮已否决） |
| D. 显式标记 | 用户在记录时勾选「算作项目推进」 | 增加记录负担，违背「快速记录」的设计目标 |

**我的倾向是 B + 时间前置**：模板块时段内通常只有一两件事，
「时长最长的那块」大概率就是主体行为；「短视频」在「干活」时段里
通常不是主体。但这会把「我工作 30 分钟、其余时间都在摸鱼」
判成摸鱼为主——**这可能是对现实的忠实反映，也可能是过度解读**。

此事取决于**你想让这套统计扮演什么角色**：是「今天有没有推进」的
存在性检查，还是「推进了多久」的量化。设计文档 §2.1 写的是
「工作日每天 45–90 分钟高质量推进即足够」——倾向后者，那方案 A 的
漏算就是真问题，值得修。

**我需要你回答的是：一句「专注写代码 30 分钟」，你希望它被算进项目推进吗？**
